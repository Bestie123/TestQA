# Универсальный промпт для AI-ассистента

> Используй этот промпт как базовый шаблон для ЛЮБОГО проекта.
> Копируй в корень проекта и адаптируй под специфику.

---

## Общие правила работы

### 1. Документация (ОБЯЗАТЕЛЬНО при каждом изменении)

В каждом каталоге, где создаёшь или редактируешь файлы, создавай/обновляй `doc.md` (или `doc/` для многофайловых). Документация должна быть удобна для чтения AI.

**Состав документации:**
- Схема архитектуры (ASCII)
- Описание всех файлов и их назначения
- Форматы данных (примеры JSON/YAML/Markdown)
- Проблемы и баги (что было сломано, как починил)
- Методы сборки и компиляции
- Какой код куда вставлял (`file:line` reference)
- Решение проблем (типичные ошибки и их решения)
- Примеры конфигов и скриптов
- Образцы заполнения (как выглядят данные)
- Связи с другими компонентами

**Логирование решений (ОБЯЗАТЕЛЬНО):** Каждое задокументированное решение (проблема, баг, фича) должно содержать:

1. **Источники анализа** — какие файлы были прочитаны для понимания проблемы (с номерами строк ключевых мест)
   - Пример: `packages/core/src/database/migration.ts:22-28` — прочитан migration runner

2. **Выполненные команды и их результат** — какие запросы к БД, MCP tools, CLI команды выполнялись и что показали
   - Пример: `bun -e "... PRAGMA table_info(session)" → Has metadata: true`
   - Пример: `curl.exe http://127.0.0.1:9222/json → page: MyApp`

3. **Отклонённые альтернативы** — какие ещё варианты рассматривались и почему не подошли
   - Пример: "Попробовал junction links → сломало包 менеджер. Решение: установить пакет напрямую"

4. **Трудности и тупиковые ветки** — что не сработало, сколько времени заняло, что было неочевидно
   - Пример: "addEventListener не работает в特定 среде → замена на onmessage"

### 2. Навигация

Поддерживай `DOC_NAV.md` — главный файл с ссылками на все `doc.md` файлы. Разделяй по компонентам/слоям.

**Перед завершением ответа:** проверь что `DOC_NAV.md` содержит ссылку на каждый существующий `doc.md` файл. Если создал новый — обнови.

### 3. Формат имени файлов документации

- Одиночный файл: `doc.md` в корне каталога
- Много файлов: `doc/` подкаталог с `*.md` файлами

### 4. После каждого изменения (ЧЕКЛИСТ)

Перед завершением каждого ответа ВЫПОЛНИ:

1. Обнови `doc.md` в каждом каталоге где были изменения (см. п.1 "Логирование решений" — обязательно укажи источники анализа, команды, альтернативы, трудности)
2. Обнови `DOC_NAV.md` если добавился новый doc-файл
3. Запусти typecheck/lint: команду сборки проекта (см. README проекта)
4. Запусти тесты: команду тестирования проекта (см. README проекта)
5. Commit с понятным сообщением
6. Проверь что нет битых симлинков в `node_modules` (см. п.7)

### 5. Стиль документации

- Используй таблицы для сравнения
- Используй блоки кода с указанием языка (` ```json `, ` ```typescript `, ` ```powershell ` и т.д.)
- Для data flow используй ASCII-диаграммы
- Для API — таблицы endpoints
- Для багов — таблица: проблема — причина — решение

### 6. Пример структуры doc.md

```markdown
# packages/xxx/ — Описание компонента

## Файлы
| Файл | Назначение |
|------|-----------|
| src/file.ts | Описание |

## Архитектура
```
ComponentA -> ComponentB -> FileSystem
```

## Форматы данных
```json
{ "example": "value" }
```

## Проблемы
| # | Проблема | Причина | Решение |
|---|----------|---------|---------|
| 1 | ... | ... | ... |

## Сборка
```powershell
npm run build
```

## Связи
- Компонент X зависит от Y через Z
```

### 7. ЗАПРЕЩЕНО: симлинки и junction links

Никогда не создавай `New-Item -ItemType Junction`, `mklink /J`, `fsutil hardlink` или любые другие файловые перенаправления в `node_modules/`. Это ломает установку пакетов.

**Правильный путь при отсутствии пакета:**
1. `npm install <package>@<version>` (или `bun install`, `yarn add` — зависит от проекта) — установить напрямую
2. Клонировать/скачать с git-репозитория — скачать свежую копию
3. Удалить lock-файл и перезапустить установку — если конфликт версий

### 8. Структура документации в репозитории

```
<project-root>/
  DOC_NAV.md              - главный навигатор (ОБЯЗАТЕЛЬНО обновлять)
  PROMPT.md               - этот файл (копировать в проект)
  ACTIVE_GOAL.md          - трекер текущей сессии
  README.md               - обзор проекта, быстрый старт
  <package-1>/doc.md      - документация компонента 1
  <package-2>/doc.md      - документация компонента 2
  docs/
    reference/             - справочники (API, SQL, форматы)
    features/              - описание фичей (≥100 строк)
    guides/                - гайды и troubleshooting
```

## Интеграция с ACTIVE_GOAL.md

При старте новой сессии ВСЕГДА:

1. Прочитай `README.md` — обзор проекта, архитектура
2. Прочитай `ACTIVE_GOAL.md` — текущая цель и статус
3. Прочитай `DOC_NAV.md` — карта документации

При завершении каждого шага:

1. Обнови `ACTIVE_GOAL.md` (дата, статус, решения)
2. Обнови `todowrite`
3. Документируй в `doc.md`
4. Обнови `DOC_NAV.md`
5. Запусти проверку сборки и тестов
6. Коммитни с понятным сообщением

## Ключевые принципы

| Принцип | Описание |
|---------|----------|
| **Контекст-ориентированность** | Всегда начинай с чтения документации проекта |
| **Инкрементальность** | Разбивай большие задачи на мелкие шаги (1-2 ответа) |
| **Документируемость** | Каждое решение — с источниками, командами, альтернативами |
| **Воспроизводимость** | Команды сборки/тестов — в README, запускай перед коммитом |
| **Непрерывность** | ACTIVE_GOAL.md — мост между сессиями, не теряй контекст |
| **Чистота** | Никогда не симлинки в node_modules, только установка пакетов |
